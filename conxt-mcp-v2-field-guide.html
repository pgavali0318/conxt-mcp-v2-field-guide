MCP Python SDK v2 · Migration & interoperability

Upgrading your MCP server to v2 — without breaking the agents.

A practical migration guide for teams running production MCP servers. The v2 SDK supports the 2026-07-28 spec — it is a major rework, not a safe dependency bump.

Scope: written for teams running Python MCP servers on Streamable HTTP, especially mounted behind FastAPI. The migration protocol and interoperability test card apply to any language; the code specifics are Python + FastAPI. stdio / local servers don't touch the transport half.

Technical specifics below were verified against a live mcp==2.0.0 install. Confirm against the official SDK before your own production rollout.

The short version

Keep production pinned to a working v1 release while you port and test v2 on a separate branch and endpoint. Installing mcp>=2 over v1 code will often install cleanly and then fail at runtime — on imports, constructor arguments, routes, startup, or identity handling. Migrate deliberately; canary; keep a v1 rollback until the observation window closes.

1What changed in SDK v2

The high-level server model is still recognizable — but construction, transport, context, and lifecycle APIs moved. These are the changes most likely to affect a FastAPI-mounted MCP server. ✓ marks items verified against mcp 2.0.0.

v1 patternv2 migrationVerified
FastMCPRenamed to MCPServer.✓
mcp.server.fastmcpModule removed. Import from mcp.server.mcpserver.✓
Transport in constructorPass host, streamable_http_path, stateless_http, json_response to streamable_http_app() (or run()).✓
Reading the requestNew: ctx.request_context.request.headers → ctx.headers. The old attribute is not guaranteed.✓
Implicit server versionPass an explicit version=.✓
Session-manager accessPublic mcp.session_manager property — created lazily, only after streamable_http_app() is called.✓
Per-request lifespanStreamable-HTTP lifespan is entered once at session-manager start, not per request.—
Auto .env loadingLoad configuration in the application itself.—

What stays familiar: stateless Streamable HTTP is still supported and carries no state between requests; tools still use @mcp.tool(); a param annotated ctx: Context is still how a tool receives context. Authentication concepts remain, but your middleware and identity propagation still need deliberate testing.

Representative port — FastAPI-mounted server

# Before (v1)
from mcp.server.fastmcp import FastMCP, Context
mcp = FastMCP("Conxt", stateless_http=True, json_response=True,
              streamable_http_path="/")
app.mount("/mcp", mcp.streamable_http_app())

# After (v2)
from mcp.server.mcpserver import MCPServer, Context
mcp = MCPServer("Conxt", version="1.2.0")
mcp_app = mcp.streamable_http_app(
    streamable_http_path="/",   # REQUIRED when mounting at /mcp:
    stateless_http=True,        # v2 default is "/mcp" -> would give /mcp/mcp
    json_response=True,
)
app.mount("/mcp", mcp_app)

Verified specifics the general guidance omits

Four things confirmed against mcp 2.0.0 that bite a FastAPI-mounted server: (1) streamable_http_app()’s default path is /mcp — mount at /mcp and you get /mcp/mcp unless you pass streamable_http_path="/". (2) Header reads move to ctx.headers; the old ctx.request_context.request path is gone, so every credential check must be updated. (3) mcp.session_manager raises RuntimeError if touched before streamable_http_app() runs — keep the mount at module top-level so it exists by the time the lifespan starts. (4) The Streamable-HTTP request-body limit defaults to 4 MiB (4194304).

Common mistake

Do not change mcp[cli]==1.x to mcp>=2 and deploy the same code. The package installs; the imports, constructor arguments, routes, startup, and identity handling do not.

2Safe migration protocol

A staged protocol so beta feedback measures interoperability — not an uncontrolled production upgrade.

  1. Freeze the baseline.Pin the working v1 dependency; capture its tool list, schemas, auth behavior, latency, and known clients.
  2. Add regression tests first.Cover initialize, tools/list, representative tool calls, invalid input, unauthorized access, startup, shutdown, and concurrent requests.
  3. Create a v2 branch.Change imports and construction; move transport settings to the app factory.
  4. Review lifecycle assumptions.Keep process-wide pools and caches in lifespan; move per-request acquisition out of it.
  5. Review identity propagation.Verify middleware-authenticated identity reaches tools through injected context. Preserve non-JWT API-key paths intentionally.
  6. Deploy staging.Separate service or hostname, separate logs, immediate rollback path.
  7. Run interoperability tests.Direct clients and gateways against the same tool set; compare schemas, error shapes, headers, and routes.
  8. Canary and cut over.Limited traffic to v2, observe, promote only after parity, retain v1 until the window closes.

Route & transport checks

Confirm both /mcp and /mcp/ behave, with no nested /mcp/mcp. Verify Content-Type, Accept, and the new routing headers (Mcp-Method, Mcp-Name). Exercise stateless mode under concurrency — never assume request state survives. Test the 4 MiB body limit. Validate DNS-rebinding / Host protections behind FastAPI, Railway, a proxy, or a gateway.

Authentication & governance checks

Reject missing, expired, malformed, wrong-issuer, and wrong-audience tokens. Keep permanent-API-key and OAuth/JWT paths distinct and observable. Pass verified identity from middleware — never trust a caller-provided user ID for shared writes. Enforce scopes at the action boundary, not only in the prompt. Log the tool, actor, tenant, authorization result, downstream action, and recovery — never secrets.

3Interoperability test card

For every real workflow. A successful tool call is not enough — the beta should demonstrate safe execution, traceability, and recovery across server boundaries.

Recommended server boundaries

Keep context & governance and universal execution as separate MCP responsibilities — clearer permissions, and each server evolves or rolls back independently.

Agent / LLMInterpret the request, gather context, propose a plan, request tools.
Context / governance MCPApproved memory, workflow rules, decisions, guardrails, required approvals.
Execution MCP / gatewayGoverned execution across business apps through one integration layer.
Business systemSystem of record and final source of action state.

The question the beta should answer

Can we reconstruct who asked for an action, which context and policy allowed it, what the execution layer performed, whether the business system committed it, and how we recovered if any step failed?

4Release gate

Do not promote v2 until all are true.

  • The SDK is constrained intentionally (v1 pinned, or v2 bounded below the next major).
  • All server imports and constructor arguments match the v2 API.
  • The final mounted MCP route is confirmed from outside the deployment network.
  • Lifespan starts and stops cleanly; shared resources initialize exactly once.
  • Every production tool appears with the expected schema and compatible output.
  • JWT/OAuth and permanent-API-key paths both pass positive and negative tests.
  • Agent, execution layer, and downstream API share a trace/correlation ID.
  • Retries are idempotent or guarded by a deduplication key.
  • A known-good v1 rollback remains available.
